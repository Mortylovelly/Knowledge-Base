# LOGGING PROTOCOL — сохранение истории и переписок

Этот документ определяет, как ассистент должен вести долговременную историю работы.

## 1. Когда создавать запись

Создавать новую numbered update-запись, когда владелец говорит:
- «сохрани»;
- «запиши в базу»;
- «сохрани логи»;
- «зафиксируй, что мы сделали»;
- «обнови память»;
- либо явно просит внести итоги этапа.

Не ждать, пока история станет слишком большой. Существенные изменения полезно документировать в конце текущего рабочего этапа.

## 2. Что именно сохранить

Каждая запись должна включать насколько возможно:
- дату (локальная дата пользователя; если неизвестно — не выдумывать);
- проект, Minecraft version, loader, Java, целевую ветку;
- номер и версию мода;
- задачу и исходный контекст;
- точные симптомы/ошибки и важные строки логов;
- что пользователь сообщил и что ассистент сам проверил;
- какие гипотезы рассматривались и почему;
- подтверждённую причину (или явную отметку, что причина не доказана);
- файлы, которые были прочитаны/изменены/созданы/удалены;
- суть изменений;
- ссылки на коммиты и commit SHA;
- GitHub Actions run ID, SHA запуска, статус/conclusion;
- факт наличия JAR artifact;
- реальные тесты в одиночном мире/клиенте/dedicated server;
- действия, которые должен выполнить владелец/друг;
- что не проверено, риски и открытые задачи;
- ссылки на связанные записи и issue/PR.

## 3. Что значит «сохранить все логи»

По умолчанию это означает максимально подробный структурированный отчёт о технической истории доступного диалога. Он должен сохранять все значимые решения, ошибочные гипотезы, неудачные попытки, исправления и результаты, чтобы их не пришлось повторять.

Это **не равнозначно дословному экспорту всего чата**: ассистент не имеет гарантированного доступа ко всем сообщениям всех прежних чатов. Нельзя выдумывать пропущенные сообщения и нельзя утверждать, что они автоматически сохранены.

## 4. Как сохранить дословные переписки

Для полного текстового архива:
1. В ChatGPT открыть Settings → Data Controls → Export Data.
2. Подтвердить экспорт и получить архив.
3. Распаковать архив локально.
4. Отобрать чаты по Minecraft-модам.
5. Загрузить исходные файлы экспорта в `archive/chat-exports/` (можно сначала положить zip/json как есть).
6. Добавить рядом README с датой экспорта, именами выбранных чатов, перечнем проектов и примечанием о том, что импортировано.
7. Не редактировать оригинальный экспорт; для удобного поиска можно дополнительно создавать очищенные Markdown-копии.

Ассистент может помочь структурировать загруженный экспорт, но не должен говорить, что старые сообщения сохранены, пока они действительно не были доступны и помещены в репозиторий.

## 5. Нумерация

Каждая новая запись получает следующий свободный номер внутри проекта:
- `001-...`
- `002-...`
- `003-...`

Номер не сбрасывается при смене версии Minecraft и не переиспользуется после исправления. Если запись была ошибочной, создать следующую запись с исправлением, а не удалять/переписывать старую историю.

Для больших проектов можно добавить подпапки по веткам/линиям, но единая хронологическая последовательность проекта должна оставаться понятной. Если разделение обязательно, явно записать правило нумерации в PROJECT.md.

## 6. После создания записи

Обязательно обновить:
1. `projects/<project>/PROJECT.md` — текущее состояние, актуальная версия и открытые задачи.
2. `PROJECTS_INDEX.md` — краткий статус.
3. Общие файлы `shared/`, если изменились универсальные сведения.
4. `START_HERE.md` — только если поменялся порядок навигации.

## 7. Стандарт качества

- Не смешивать план с реализацией.
- Не смешивать успешную сборку с успешным тестом.
- Не смешивать слова пользователя с независимо подтверждёнными фактами.
- Каждое утверждение о коде по возможности снабжать GitHub ссылкой.
- Использовать точные SHA, версии и пути.
- Если факт неизвестен, написать «не установлено».
- Все будущие записи должны быть понятны человеку, который впервые открыл репозиторий.
