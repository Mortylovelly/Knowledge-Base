## Запланированная концепция — не реализовано

### Уникальная идентичность предмета
После регистрации предмет получает:
- UUID;
- уникальный последовательный номер, например UR-000001;
- автора/создателя;
- дату регистрации;
- историю предмета.

Номер должен назначаться на сервере, а не клиентом. Идентичность уникальна в пределах мира/сервера, пока не спроектирована глобальная база.

### Редкости
Предлагались:
- COMMON
- UNCOMMON
- RARE
- EPIC
- LEGENDARY
- MYTHIC

Регистрируемые предметы могут иметь любую редкость, разрешённую шаблоном. Редкость — прежде всего статус/визуальное оформление/коллекционность; в первой версии не планировалось автоматически усиливать боевые характеристики.

### Надписи
Дополнительная платная/расходуемая функция: постоянная цветная пользовательская надпись/имя предмета. Планировались латиница/кириллица/цифры и ограничение примерно 24 символа. Ввод нужно очищать от управляющих/форматирующих символов. Изменять надпись повторно — только через новый расходуемый предмет/операцию.

### Интерфейс
Предпочтителен интерфейс управления через кузнечный стол, но нельзя перехватывать или заменять ванильный smithing экран. Планировался отдельный Unique Relics GUI, открываемый согласованным способом, чтобы не ломать Elytra Trims / Trims on Tools.

### Шаблоны
- Печать регистрации — для первой регистрации.
- Шаблоны/матрицы редкости с максимальным доступным уровнем.
- Свиток для надписи.
- Ограниченное количество применений.
- Возможность получения рецептов через фрагменты — идея требует дальнейшего проектирования.

### Будущие дополнительные функции
- История предмета.
- Коллекция реликвий игрока.
- Визуальные эффекты редкости и подсказки.
- Однотипный предмет после регистрации должен иметь stack count 1.
- Данные предполагалось хранить в NBT для Minecraft 1.20.1 (не использовать Data Components из новых версий Minecraft).

## Совместимость
Приоритет: Elytra Trims и Trims on Tools. Не разрушать существующие trim NBT/data и не заменять ванильное поведение кузнечного стола.

## Что нужно сделать при возобновлении
1. Проверить реальный HEAD и build status.
2. Прочитать текущую структуру и подтвердить, какие файлы действительно есть.
3. Уточнить способ открытия отдельного интерфейса без конфликтов smithing.
4. Спроектировать безопасную серверную регистрацию UUID/serial и persistent world counter.
5. Реализовывать поэтапно, пока владелец не попросил начать.
