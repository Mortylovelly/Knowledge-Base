# WORKFLOW — пошаговый процесс разработки

Документ описывает обычный цикл совместной работы.

## A. Начало задачи

1. Прочитать стартовые правила базы.
2. Выбрать правильную папку в `projects/`.
3. Прочитать `PROJECT.md` и связанные записи `updates/`.
4. Открыть исходный GitHub-репозиторий.
5. Проверить default branch, список веток, последние коммиты, статус репозитория.
6. Найти ветку, которая соответствует версии Minecraft, поставленной в задаче.
7. Прочитать `gradle.properties`, `build.gradle`, `settings.gradle`, `fabric.mod.json`, mixin config, workflow и исходные Java-файлы по теме.

## B. Диагностика бага

1. Зафиксировать точный симптом и момент появления.
2. Разделить серверный лог, клиентский лог, crash report, disconnect reason.
3. Выделить первую причинную ошибку и цепочку `Caused by`; не ориентироваться только на последнюю строку.
4. Проверить точные версии Minecraft, Loader, API и конфликтующих модов.
5. Сравнить работающий и неработающий набор модов.
6. Сформулировать несколько гипотез, если причин может быть несколько.
7. Проверить гипотезу по исходному коду, API или минимальным тестом.
8. Исправлять только то, что имеет доказанную или наиболее сильную связь с причиной.

## C. Изменение

1. Сначала прочитать полный исходный файл.
2. Проверить вызываемые методы и данные, которыми он оперирует.
3. Сделать минимальное изменение.
4. Проверить Mixin target/descriptors и конфиг, если затрагивались миксины.
5. Проверить ресурсы и metadata: id мода, версия, зависимости, entrypoints.
6. Проверить diff и убедиться, что случайно не затронута другая версия/ветка.
7. Сохранить коммит с понятным сообщением.

## D. Сборка

1. Использовать workflow проекта и его целевые версии Java/Gradle.
2. Дождаться выполнения Actions.
3. Сверить commit SHA запуска с HEAD целевой ветки.
4. Открыть job logs при неудаче.
5. Если сборка успешна — проверить artifact (имя/наличие).
6. Если после успешной сборки появился новый коммит, проверить Actions ещё раз для нового SHA.

## E. Тест в Minecraft

Указывать точную конфигурацию теста:
- версия Minecraft;
- loader и Fabric API;
- версии тестируемых модов;
- клиент/одиночный мир/выделенный сервер;
- список дополнительных модов, если он известен;
- новый или существующий мир;
- последовательность воспроизведения;
- результат и логи.

Тест, который владелец/друг выполнил самостоятельно и сообщил в чате, документируется как пользовательский тест. Не выдавать его за собственный.

## F. Выдача результата

В итоговом сообщении кратко написать:
- что было не так;
- какие файлы изменены;
- ссылка на коммит/ветку;
- результат Actions;
- ссылка на JAR artifact, если доступен;
- какие проверки ещё нужны;
- точные шаги установки/тестирования.

## G. Сохранение в Knowledge Base

Для каждого существенного завершённого этапа создать следующий файл `updates/NNN-название.md`, используя [шаблон](../templates/UPDATE_TEMPLATE.md).

Затем:
- обновить блок «Текущее состояние» и таблицу файлов в `PROJECT.md`;
- обновить `PROJECTS_INDEX.md`;
- при изменении общих правил/версий обновить соответствующий файл в `shared/`;
- не удалять прошлые записи.

## H. Правило «сохрани все логи»

Когда владелец говорит сохранить логи:
- Сохранить полную доступную техническую хронологию из текущего чата: что обсуждали, что проверяли, что предполагали, что меняли, какие ошибки были, какие коммиты и сборки получились.
- Включать существенные решения и отказанные подходы, если они помогут не повторять ошибку.
- Не писать вымышленные выводы.
- Не считать, что ChatGPT автоматически имеет доступ ко всей истории всех чатов.
- Для дословных сообщений импортировать официальный экспорт ChatGPT в `archive/chat-exports/`; в проектную историю добавить ссылку/описание относящегося к моду диалога.
