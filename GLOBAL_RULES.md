# GLOBAL RULES — обязательные правила работы

Эти правила относятся ко всем Minecraft-проектам Mortylovelly.

## 1. Пользовательский workflow

Владелец не программист и обычно работает через GitHub в браузере и GitHub Actions.

Поэтому ассистент должен:
- По возможности самостоятельно изучать и изменять подключённые GitHub-репозитории.
- Не заставлять владельца вручную копировать проект целиком, если файлы доступны через GitHub.
- Давать прямые инструкции по-русски.
- Если всё же требуется ручное действие, указывать точный путь в репозитории, что создать/заменить/удалить и давать полный текст файла, а не отдельный фрагмент.
- Использовать актуальный файл из GitHub как источник истины; пользовательский файл, присланный в текущем чате, также считать источником истины для конкретной обсуждаемой версии, пока он не сверён с репозиторием.

## 2. Перед работой

Всегда выяснить:
1. Какой именно мод обсуждается.
2. Его GitHub-репозиторий.
3. Целевую ветку и версию Minecraft.
4. Текущий HEAD-коммит и незавершённые изменения, если доступны.
5. Версии Java, Fabric Loader/API, Loom, Gradle и другие зависимости из файлов проекта.
6. Есть ли уже открытые PR/Actions и не идёт ли сборка.

Не переносить конфигурацию из одного проекта в другой без проверки. Особенно не смешивать Minecraft 1.20.1 / Java 17 и Minecraft 1.21.1 / Java 21.

## 3. Работа с кодом

- Полностью прочитать затрагиваемые файлы до изменения.
- Понять существующую механику и зависимости вызовов.
- Сохранять уже работающие функции и архитектуру.
- Вносить минимальные, целевые изменения. Не проводить попутный рефакторинг без необходимости.
- Не удалять код только потому, что он кажется ненужным; сначала выяснить его назначение.
- Для пользовательских изменений предпочтительны полные проверенные файлы.
- Не придумывать классы, методы, API, Mixin targets, версии библиотек или пути.
- Не использовать устаревший Minecraft API, если версия целевого проекта уже известна.
- Для Minecraft 1.20.1 использовать NBT-подходы там, где Data Components ещё не доступны; не переносить API из более новых версий.
- Если изменение затрагивает сетевые пакеты, реестры, генерацию мира, сохранения или синхронизацию, отдельно оценить server/client consistency и совместимость с другими модами.

## 4. Версии и ветки — критически важно

- Всегда менять только ветку нужной версии.
- Для SkyLimitless 1.20.1 это `minecraft-1.20.1-fabric`, а не `main`.
- SkyLimitless `main` — отдельная линия проекта 1.21.1 Fabric; не смешивать её с 1.20.1.
- Для каждого другого проекта заново проверять целевую ветку по репозиторию.
- Номер версии Minecraft, Java и Fabric в файлах и workflow должен быть согласован.
- Не выпускать JAR с тем же номером версии, если изменение предназначено как отдельное исправление уже опубликованной версии; увеличить mod_version согласно истории проекта.

## 5. Сборка и проверка

Последовательность:
1. Внести изменение.
2. Проверить diff и итоговые файлы.
3. Запустить/дождаться GitHub Actions для конкретного commit SHA.
4. Проверить, что workflow завершился с `conclusion: success`.
5. Убедиться, что успешный run относится именно к последнему commit SHA, а не к промежуточному коммиту.
6. Убедиться, что артефакт JAR опубликован, если workflow его создаёт.
7. Только после этого говорить, что сборка прошла.

Важно различать:
- **Сборка прошла** — Gradle build завершился успешно.
- **Тест в игре прошёл** — мод реально проверили в клиенте/мире.
- **Серверная совместимость проверена** — клиент подключался к выделенному серверу с конкретным набором модов.
- **Конфликт устранён** — воспроизводившаяся проблема проверена после исправления.

Успешная сборка не доказывает работоспособность всех механик и совместимость с модпаком.

Не обвинять конкретный мод без соответствующих логов/экспериментов. Сравнивать минимальные воспроизводимые наборы модов, полные логи и точные версии.

## 6. GitHub Actions и диагностика

- Проверять workflow конкретной ветки.
- При ошибке смотреть полный job log, а не только статус.
- Фиксировать commit SHA, run ID, ссылку, статус и вывод.
- Ошибка компиляции отличается от ошибки загрузки мода и от runtime-ошибки.
- Если run ещё выполняется, так и сообщать; не называть его успешным.
- Не подменять отсутствие тестирования предположением, что всё исправлено.

## 7. Объяснение владельцу

- Сначала объяснить проблему простыми словами, затем техническую причину.
- Прямо говорить, что было подтверждено, а что является гипотезой.
- Не перегружать пользователя ненужным жаргоном.
- Для ручной установки указывать, где заменить JAR и какие версии должны совпадать на сервере и клиентах.
- Перед опасными операциями с миром, сохранениями или конфигами советовать резервную копию.
- Не предлагать удалять/пересоздавать мир без доказанной необходимости.

## 8. Документирование

После существенного этапа обновлять Knowledge Base по просьбе владельца или когда он прямо просит «сохрани/запиши».

Не переписывать историю так, будто гипотеза изначально была доказанным фактом. В update-файлах использовать явные статусы:
- Подтверждено
- Вероятная причина
- Гипотеза
- Не проверено
- Исправлено в коде
- Сборка прошла
- Проверено в игре
- Требуется проверка владельцем

## 9. Что нельзя считать известным

Если точный список модов, команда, координаты, версия, конфиг или результат теста не зафиксирован в базе/репозитории/логе — не выдумывать его. Указывать «не сохранено / требуется проверить».

Эта база пополняется. Более свежие подтверждённые сведения в GitHub имеют приоритет над устаревшими записями, но разницу следует задокументировать.
